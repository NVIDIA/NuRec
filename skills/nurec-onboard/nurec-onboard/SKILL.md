# NuRec Onboard

**Source execution:** Read `$NUREC_WORKDIR/nurec-runtime.md`, generated by
`run.sh`, before executing commands. For every root-workspace `bazel` command
below, use its literal Docker/Bazel prefix with the same target and arguments.
Only the standalone converter workspace runs Bazel on the host. Do not extract
release archives into host caches or invent module overrides.

This is the operating specification for an autonomous workflow orchestrator that runs a
conditional dataset audit, then builds an NCore V4 converter, validates its output, and
runs NuRec reconstruction.
The agent reads this file and executes the full workflow without user interaction.

---

## 1. Input Schema

```yaml
# Required
data:
  name: <string> # Short dataset identifier, filesystem-safe (alphanumeric, dash, underscore)
  path: <string> # Path to raw sensor data
  description: <string> # Short high-level overview of the dataset.

  # Optional
  # Dataset documentation: each entry is a file path, URL, or inline text.
  # Pass a single string for one source, or a list for multiple (paper +
  # devkit + datasheet, etc.). All entries are read and cited individually in
  # critical_parameter_justifications evidence.
  docs: <string> | [<string>, ...]
  # Optional structured dataset facts from audit-dataset. Evidence-backed
  # facts are authoritative; UNRESOLVED high-risk facts are hypotheses for
  # downstream verification. Keep `description` high-level and
  # non-duplicative.
  profile: <mapping>

ncore:
  camera_ids: [<string>, ...] # Optional conversion camera scope.
  lidar_ids: [<string>, ...] # Optional conversion LiDAR scope.
  seek_sec: <number|null> # Optional conversion start offset.
  duration_sec: <number|null> # Optional conversion duration.
  converter_dir: <string|null> # Default: $NUREC_WORKDIR/ncore-<data.name>
  output_dir: <string|null> # Default: <ncore.converter_dir>-out
nurec:
  camera_ids: [<string>, ...] # Optional reconstruction camera scope.
  lidar_ids: [<string>] # Exactly one LiDAR for now.
  output_dir: <string|null> # Default: <ncore.converter_dir>-nurec-out
  dev_deps_image: <string|null> # Optional; defaults to the checkout's build-image pin.
  source_dir: <string|null> # Optional; defaults to the enclosing checkout.
execution:
  max_inner_iterations: <int> # Default from defaults.yaml.
  max_outer_iterations: <int> # Default from defaults.yaml.
  max_config_iterations: <int> # Default from defaults.yaml.

# Optional inline audit controls. The workflow runs audit-dataset automatically
# when data.profile is absent; set enabled: true to force a re-audit even when
# data.profile is already present. Standalone audit remains the preferred user
# path when unresolved dataset facts need operator or data-owner review.
audit:
  enabled: <bool> # Optional force-on override.
  output_dir: <string> # Default: $NUREC_WORKDIR/audit-<data.name>
  # Default true; stop before build when a blocking unresolved fact remains.
  # An unresolved fact a converter can derive is advisory and never stops the
  # workflow.
  fail_on_unresolved: <bool>
```

This shares the core `ncore` input schema with `build-ncore-converter`, then
adds top-level `nurec`, `execution`, and `audit` blocks for reconstruction,
loop limits, and optional audit pre-flight. The top-level `ncore` block scopes
conversion and validation steps; the top-level `nurec` block scopes
`run-nurec`. If `data.profile` is absent, run `audit-dataset` before applying
scope checks. After the audit decision (and after reloading generated audit
input when audit ran), fail the workflow early if `nurec.lidar_ids` is missing
or does not contain exactly one entry when NuRec is requested, or if exactly
one of a scoped `ncore.seek_sec` / `ncore.duration_sec` pair is present.

### Optional structured facts in `data.profile`

`data.profile` is an optional structured profile generated by `audit-dataset`
or authored by an operator. When present, downstream steps should read it
before `data.description`. Evidence-backed facts in the profile are the
authoritative dataset facts. Fields marked `UNRESOLVED:` -- especially
high-risk geometric and optical facts from audit-dataset -- are hypotheses that
downstream steps must re-verify through critical-parameter justifications
rather than silently treating as truth. `data.description` remains a short
overview for orientation, not a second copy of the same details.

Expected `data.profile` sections:

- `file_layout`
- `calibration_and_frames`
- `pose_sources` (list of pose-source records)
- `timestamp_semantics`
- `cameras` (list of camera records)
- `lidars` (list of LiDAR records)
- `cuboids`
- `known_gaps`

### Optional enrichment for `data.description`

`data.description` is free-form prose. For audit-generated inputs, keep it to
a high-level overview and put detailed facts in `data.profile`. When an input
does not provide `data.profile`, including any of the following in
`data.description` shortens exploration and removes ambiguity the agent would
otherwise have to infer:

- **Documentation pointers** beyond what `data.docs` already links -- specific sections,
  page anchors, or vendor datasheets the agent should prefer.
- **Known-quirky sensor conventions**: non-standard native axis mapping, a spinning LiDAR
  that ships per-beam azimuth offsets, an unusual cuboid centroid convention, an unusual
  frame-timestamp reference (center vs start vs end), or any other convention the agent
  should not have to re-derive.
- **Known calibration file locations or field names** that are hard to find from directory
  layout alone -- e.g. the per-beam elevation table path, the extrinsics file, a
  column-azimuth table when shipped.
- **Known per-ray metadata naming scheme** when it differs from common patterns (`ring`,
  `ring_id`, `channel`, `azimuth`, per-point `timestamp`, `intensity`, ...).
- **Known gotchas or prior-run issues** the operator wants the agent to account for -- e.g.
  a sensor known to log in the wrong frame, a known calibration mismatch, or a field known
  to be unreliable.

For the full catalog of things `build-ncore-converter` discovers on its own, see
[`build-ncore-converter` raw-data exploration](steps/build-ncore-converter/SKILL.md#parse-input-and-infer-sensor-properties)
and [`build-ncore-converter/conventions.md`](steps/build-ncore-converter/conventions.md).

## 2. Execution Flow

```
audit-dataset (auto when data.profile absent) ->
build-ncore-converter (scaffold) -> validate-ncore-data -> run-nurec
        ^                                  |                    |  ^
        |   diagnosis: converter issues    |                    |  |
        +----------------------------------+                    |  |
        |          diagnosis: NCore data issues                 |  |
        +-------------------------------------------------------+  |
                                                                   |
                diagnosis: NuRec config issues (config-fix loop) --+
```

Each step reads its own `SKILL.md` and executes it inline. Each step receives
the relevant scoped fields from the workflow input.

### Audit the dataset

If `data.profile` is absent, run `audit-dataset` first with the current input.
A present `data.profile` is the only automatic skip signal: the input is
treated as already audited, even if the sensor scope was hand-authored. Set
`audit.enabled: true` to force a re-audit when `data.profile` is already
present. `audit.enabled: false` is not a force-skip override; a profile-less
input still runs audit. Validate the generated input YAML, data-quality report,
and `audit_profile.json` using the audit step-boundary validator:

```bash
cd "$NUREC_ONBOARD_DIR" && bazel run //skills/nurec-onboard/validators:audit_dataset_validator -- \
  <audit_output_dir>/<data.name>_input.yaml \
  <audit_output_dir>/<data.name>_data_quality_report.md \
  <audit_output_dir>/audit_profile.json
```

After validation succeeds, reload the generated input YAML and use it as the
effective input for downstream steps.

### Gate on unresolved high-risk facts

Apply this gate on every path, to a hand-authored `data.profile` exactly as to
one audit generated. A profile that skipped the audit step has had no more
review than one that did not, so scanning only audit output would leave the
hand-authored case unchecked.

Scan the effective input for `UNRESOLVED:` entries and split them by severity:

- **Blocking** -- the entry sits at a high-risk field that only a human or data
  owner can answer, per
  ["Blocking vs converter-derivable"](steps/audit-dataset/SKILL.md#blocking-vs-converter-derivable).
  Record their YAML paths under
  `steps.audit-dataset.unresolved_issues.critical_gaps` and their count under
  `steps.audit-dataset.summary.blocking_unresolved_count`.
- **Advisory** -- every other unresolved entry, including a high-risk field
  whose marker names the raw artifact and procedure that derives it. Record the
  YAML paths under `steps.audit-dataset.summary.advisory_unresolved`. These do
  not stop the workflow and a run carrying only these can still exit `success`.

Set `steps.audit-dataset.summary.unresolved_count` to the total across both.

If any blocking entry remains and `audit.fail_on_unresolved` is true, stop
before `build-ncore-converter` and emit a Workflow Summary with
`workflow_status: partial_success` and `steps_completed: [audit-dataset]`.

If audit does not run, omit `audit-dataset` from `steps_completed` and set
`steps.audit-dataset.runs: []`. Record whether the input carried `data.profile`
at entry in the summary's top-level `data_profile_present`; a `false` value
requires `audit-dataset` to have run, which is how the validator enforces that a
profile-less input audits before reaching scope checks or any later step.

### Build the converter

Run `build-ncore-converter` in **scaffold mode**, passing the workflow input as-is.
Outputs: resolved `ncore_converter_dir`, a working converter, NCore V4 data in `ncore_output_dir`, and a `sequence_meta` JSON path.

### Validate the output

Run `validate-ncore-data` with `ncore.converter_dir: <ncore_converter_dir from build output>` and `data: { ncore_path: <sequence_meta>, raw_path: <data.path>, description: <data.description>, profile: <data.profile if present> }`.
Outputs: a diagnosis with `status`, `converter_issues`, `input_data_issues`.

### Handle validation diagnosis

**Validation-diagnosis entry rule.** If `validate.py` exit code was non-zero,
`status` MUST be in `{converter_issues, both}` and the inner fix loop
runs at least once. Failed validation is never pure `input_data_issues`;
if an upstream data issue is also suspected, classify as `both` and quote
the relevant criteria from
[`validate-ncore-data/common-failures.md`](steps/validate-ncore-data/common-failures.md)
under `steps.validate-ncore-data.unresolved_issues.converter[*].demotion_criteria_failed`.

**Validation-diagnosis entry validator (mandatory)**: before branching on `status`, re-run
the validate-ncore-data step-boundary validator against the diagnosis YAML
returned by `validate-ncore-data`:

```bash
cd "$NUREC_ONBOARD_DIR" && bazel run //skills/nurec-onboard/validators:validate_ncore_data_validator -- <diagnosis.yaml>
```

This is the consume-side re-check (the same script also runs as `validate-ncore-data`'s
own emit validator). Refuse to advance to `run-nurec` if the validator exits non-zero
and the inner fix loop has not yet been entered. A guarded second call
is intentional: it catches the case where `validate-ncore-data`'s emit validator was
patched out, or where the diagnosis YAML was edited between steps.

Branch on `status`:

- **`pass`** → run the `run-nurec` step.
- **`converter_issues`** → enter the inner loop (`validate-ncore-data` → `build-ncore-converter` fix → `validate-ncore-data`).
- **`input_data_issues`** → inspect `unresolved_issues.input_data[*].severity`.
  Skip the `run-nurec` step only when any remaining upstream issue has
  `severity: error`; if all remaining issues are `severity: warning`, run
  `run-nurec` and record the warnings under
  `steps.validate-ncore-data.summary.advisory_warnings`. That field is
  advisory (non-blocking): reserve `steps.validate-ncore-data.unresolved_issues.input_data`
  for `severity: error` findings that actually blocked `run-nurec`, so a run
  carrying only warning-severity input-data findings can still exit `success`.
- **`both`** → enter the inner loop first; after converter issues are resolved,
  apply the same input-data severity gate above to the remaining upstream
  data issues.

Use `common-failures.md` as the single source for demotion criteria; do
not restate those criteria here.

### Run NuRec reconstruction

Run `run-nurec` with `ncore.converter_dir` from the build output, `data: { ncore_path, description, profile: <data.profile if present> }`, and the `nurec` runtime fields from input (defaulting where unset).
Outputs: reconstruction metrics and a diagnosis with
`reconstruction_status: success | issues_detected`,
`ncore_data_issues`, and `nurec_config_issues`.

### Handle reconstruction diagnosis

**Reconstruction-diagnosis entry validator (mandatory)**: before branching on the run-nurec
diagnosis, re-run the run-nurec step-boundary validator:

```bash
cd "$NUREC_ONBOARD_DIR" && bazel run //skills/nurec-onboard/validators:run_nurec_validator -- <diagnosis.yaml>
```

This mirrors the validation-diagnosis consume-side check. Refuse to branch if the validator
exits non-zero; the workflow cannot safely choose the outer loop vs.
config-fix loop from a malformed diagnosis.

**Val-artifact existence backstop (mandatory, runs before branching on
the validator-checked diagnosis).** Independent of what `run-nurec` reports, glob
`<nurec_output_dir>/*/val/metrics.yaml` for the most recent run-id. If
`metrics.yaml` is absent, NuRec produced no validation metrics; treat this
as **`ncore_data_issues`** and feed it into the outer fix loop with a
cross-sensor alignment diagnosis. `pred_*.mp4` files are optional auxiliary
evidence only.

After the backstop, branch on the diagnosis status and issue buckets:

Branch on `severity: error` entries, not on whether a bucket is non-empty: a
successful run carries its `severity: warning` findings in the same buckets, and
an error in one bucket must not be routed by a warning in the other. A
`severity: warning` entry selects no branch and is not copied into
`steps.run-nurec.unresolved_issues.*` -- a finding the run survived is not
unresolved, so recording it there would block `success` for a run that met it.

- **`reconstruction_status: success`** (and `metrics.yaml` present) → emit the Workflow Summary.
- **`reconstruction_status: issues_detected` with a `severity: error` entry in `ncore_data_issues`** → enter the outer loop (`run-nurec` → `build-ncore-converter` fix → `validate-ncore-data` → `run-nurec`).
- **`reconstruction_status: issues_detected` with `severity: error` entries only in `nurec_config_issues`** → enter the config-fix loop (`run-nurec` config edit / Hydra override → `run-nurec`). `run-nurec` config issues (wrong static/dynamic variant, sensor-ID mismatch, `label_classes` / `track_label_sources` gating, etc.) are resolved by re-selecting a bundled config or by editing a custom config and applying Hydra overrides -- no converter rebuild or re-validation is required. Only record as a partial success if the loop exhausts its iteration cap.
- **`severity: error` entries in both buckets** → enter the outer loop first (converter must be correct before config tuning is meaningful), then enter the config-fix loop on the next `run-nurec` result.

## 3. Feedback Loops

Each loop invokes the relevant fix path, then re-runs the downstream check. The configured cap is the only normal early-exit boundary for an unresolved loop: continue applying concrete fixes and re-checking until the downstream check passes or the cap is reached. If the iteration cap is reached, record remaining issues in the workflow summary and proceed.

### Inner loop: validate → build (fix) → validate

Triggered by `converter_issues`. Pass:

```yaml
ncore_converter_dir: <build output>
data:
  path: <data.path>
  description: <data.description>
  profile: <data.profile if present>
diagnosis:
  source: validate-ncore-data
  errors: <converter_issues[].error>
  metrics: <eval_metrics>
  suggested_fixes: <converter_issues[].suggested_fix>
```

Repeat until validation passes or `execution.max_inner_iterations` (default from `defaults.yaml`) is reached. The iteration cap is the stopping condition: do not stop early based on judgment about likely fixability, expected runtime, or confidence in the current diagnosis. If the cap is reached with validation still failing, record the remaining validate.py failures under `steps.validate-ncore-data.unresolved_issues.converter`.

### Outer loop: run-nurec → build (fix) → validate → run-nurec

Triggered by `ncore_data_issues`. Pass a `diagnosis` with `source: run-nurec`, `errors: <ncore_data_issues[].symptom>`, `metrics: <reconstruction metrics>`, `suggested_fixes: <ncore_data_issues[].likely_cause>`. Re-validate (inner loop as needed) then re-run NuRec; repeat up to `execution.max_outer_iterations` (default from `defaults.yaml`).

### Config-fix loop: run-nurec (apply config fixes) → run-nurec

Triggered by `nurec_config_issues` when no `ncore_data_issues` are present. Do **not** rebuild the converter or re-validate -- the shard is good.

1. For each `nurec_config_issues[].likely_cause`, apply the matching fix from the [`run-nurec` config-selection playbook](steps/run-nurec/SKILL.md#select-or-create-app-config) before re-launching:
   - Wrong static/dynamic variant → re-select a `*_dynamic*.yaml` (or `/model: gaussians/composite/dynamic_gaussians`) and restart.
   - Sensor-ID mismatch **or bundled config omits a shard sensor** → enumerate **every** camera / LiDAR in the sequence meta JSON and apply as Hydra overrides (`'dataset.camera_ids=[...]'` / `'dataset.lidar_ids=[...]'`) for bundled configs, or edit them into the custom-config YAML (do not pass both -- see [`run-nurec` launch](steps/run-nurec/SKILL.md#run-nurec-reconstruction)). Sensors not listed are silently dropped.
   - `track_label_sources` gating → `'dataset.cuboid_tracks_params.track_label_sources=null'` or pin to the sources present in the shard.
   - `label_classes` missing a shard class → read the config in the selected source checkout (`configs/apps/<selected>.yaml`), write the output to `custom_config.yaml`, extend the allow-list, mount it at launch.
2. Re-invoke `run-nurec` with the updated config/overrides (after config selection only -- auxiliary data does not need regenerating).
3. Repeat until `reconstruction_status: success` or `execution.max_config_iterations` (default from `defaults.yaml`). On cap, record the remaining `nurec_config_issues` in the summary as a partial success.

## 4. Workflow Exit Conditions

The exit condition is a deterministic decision tree, evaluated top-down
once the build, validation, and reconstruction handling steps have run. The first matching branch wins; later branches
are not evaluated. Exit conditions feed directly into the Workflow Summary's `workflow_status` field, which `nurec_onboard_validator`
asserts against the rest of the summary at emit time.

Evaluate these conditions in order; the first match determines
`workflow_status`.

| Condition                                                                                                                                                   | `workflow_status` | Required summary record                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------- |
| NuRec val artifacts are missing after NuRec ran (`len(steps.run-nurec.runs) > 0` and `steps.run-nurec.val_artifact_backstop.metrics_yaml_present == false`) | `failure`         | Record the missing-artifact paths under `steps.run-nurec.val_artifact_backstop.checked_paths`.             |
| Inner loop hit its cap (`steps.validate-ncore-data.summary.iterations >= execution.max_inner_iterations`) and validation still failed                       | `partial_success` | Record the remaining validate.py failures under `steps.validate-ncore-data.unresolved_issues.converter`.   |
| Outer loop hit its cap (`steps.run-nurec.summary.iterations >= execution.max_outer_iterations`)                                                             | `partial_success` | Record NCore data issues that resisted re-conversion under `steps.run-nurec.unresolved_issues.ncore_data`. |
| Config-fix loop hit its cap (`steps.run-nurec.summary.config_iterations >= execution.max_config_iterations`)                                                | `partial_success` | Record remaining NuRec config issues under `steps.run-nurec.unresolved_issues.nurec_config`.               |
| Validation passed and reconstruction succeeded                                                                                                              | `success`         | Ensure every step-local `unresolved_issues.*` bucket is empty.                                             |
| None of the above matched                                                                                                                                   | `partial_success` | Record an explanation in some step-local `unresolved_issues` bucket; silent partial success is invalid.    |

Notes:

- The val-artifact check is independent of `reconstruction_status`: the reconstruction
  handler explicitly globs `metrics.yaml`, so missing metrics override a falsely reported
  `success` from `run-nurec`.
- `failure` is reserved for unrecoverable states where NuRec produced no validation
  metrics. Iteration caps map to `partial_success`, because the operator needs the
  remaining diagnostics rather than a bare failure.
- The final catch-all row is only a backstop. The validator rejects silent
  `partial_success`; some step-local `unresolved_issues.*` bucket must explain why
  the workflow did not meet the `success` row.
- Advisory warnings do not block `success`. Warning-severity input-data findings
  from a `validate-ncore-data` `input_data_issues` diagnosis that did not stop
  `run-nurec` (see the `input_data_issues` branch above) are recorded under
  `steps.validate-ncore-data.summary.advisory_warnings`, not in any
  `unresolved_issues.*` bucket. The `success` row's "every step-local
  `unresolved_issues.*` bucket is empty" requirement therefore still holds for a
  run that succeeded with advisory warnings.

## 5. Workflow Summary

At completion, produce a structured summary. The shown fields are the
contract; `validators/nurec_onboard_validator.py` is the executable authority for
field shape and cross-field invariants.

Each step section owns its run attempts plus its step-specific summary and
diagnostics. Keep run stats lightweight: each attempt records the host-clock
wall time it consumed. CPU stats are not tracked, and GPU stats are left to
NuRec's own training/validation metrics.

### Timestamp capture rules

Mandatory for every step attempt. A step attempt covers **every
action the agent performs to advance that step on a given
iteration**, not just the subprocess that closes it. Scaffolding, code edits, lockfile regeneration, probe
scripts, and smoke tests are all **inside** the attempt window. The
closing subprocess (`bazel run`, `docker run … nre`, etc.) is one
action _inside_ that window, not the window itself.

- Capture `started_at` **immediately before the first action of the
  attempt** at the entry anchor named in the corresponding sub-SKILL
  (e.g. `started_at=$(date -u +%FT%TZ)` in shell, or the equivalent UTC
  ISO8601 timestamp from the agent's clock).
- Capture `ended_at` **immediately after the final action of the attempt**
  at the exit anchor named in the corresponding sub-SKILL, regardless of
  whether the attempt succeeded, failed, or errored.
- Compute `duration_sec` from those two timestamps.
- Do **NOT** narrow the window to the closing subprocess; that
  actively misreports step cost.
- Do **NOT** reconstruct timestamps from file mtimes or log parsing
  after the fact -- those drift from the host clock by seconds to
  minutes (container startup, fsync, timezone) and conceal failed
  attempts that produced no artifacts.

Worked example -- a `build-ncore-converter` scaffold-mode attempt
where `duration_sec` spans the full scaffold pass, not just the
closing `bazel run`:

```yaml
runs:
  - attempt: 1
    status: success
    # Entry anchor: before parsing input.
    started_at: "2026-05-06T05:00:12Z"
    # Exit anchor: after build_ncore_converter_validator returned 0.
    ended_at: "2026-05-06T05:11:43Z"
    # ~11.5 min scaffold pass; bazel run was ~71s of that.
    duration_sec: 691.0
```

`steps_completed` and `runs[*]` must agree (bidirectional invariant):

- `steps_completed` lists every step that executed at least once during
  this run. The valid step names match the keys of `steps.*`:
  `audit-dataset`, `build-ncore-converter`, `validate-ncore-data`, and
  `run-nurec`.
- **Forward**: for every step listed in `steps_completed`, that step's
  `runs:` list MUST contain at least one entry. The
  `nurec_onboard_validator` rejects a summary that lists a completed
  step with empty `runs:`.
- **Reverse**: for every step with at least one `runs[*]` entry, that
  step MUST appear in `steps_completed`. The validator rejects a summary
  with timed runs for a step that is omitted from `steps_completed`.
- A step that legitimately did not run (e.g. `run-nurec` skipped after
  `validate-ncore-data` returned `input_data_issues`) MUST be omitted from
  `steps_completed` AND MUST have `runs: []`. Empty `runs:` is permitted
  only in this case, and only paired with omission from `steps_completed`.

Terminology: `runs` is the per-step attempt audit log -- one entry per
step invocation, including retries and failed/error attempts when they are
observable. `summary.iterations` and `summary.config_iterations` are loop
counters paired with the matching `max_*_iterations` caps recorded under
top-level `execution` (inner validate-fix cycles, outer run-nurec-fix cycles,
and config-fix retries). These fields are informative except where an exit
condition claims cap exhaustion: keep them consistent with the work performed,
and record the effective caps so the validator can reject premature
`partial_success` summaries.

For the full field-by-field schema (all `steps.*` sections, `execution` caps,
`val_artifact_backstop`, and `output_paths`) and the mandatory emit-time backstop
validator, see [workflow-summary.md](workflow-summary.md). Run that backstop
(`bazel run //skills/nurec-onboard/validators:nurec_onboard_validator -- <workflow_summary.yaml>`)
before returning the summary; a non-zero exit is a hard failure.

## 6. Constraints

- **No user interaction**: the workflow runs fully autonomously. All issues are recorded in the summary.
- **Iteration caps**: `execution.max_inner_iterations`, `execution.max_outer_iterations`, and `execution.max_config_iterations` default from [`../defaults.yaml`](../defaults.yaml).
- **Step execution**: do not delegate steps to sub-agents via the Agent/Task tool; execute each step inline, while still allowing direct invocation of necessary local subprocesses such as `bazel run` and `docker run`.
- **No git writes**: do not commit or push changes.
